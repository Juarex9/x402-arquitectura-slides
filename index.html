01 · El problema

Pagar en internet es lento

HOY · PARA USAR UNA API PAGA
  1. Crear una cuenta
  2. Cargar medio de pago / KYC
  3. Comprar créditos o suscripción
  4. Gestionar API keys
  5. Pagos lentos y contracargos
CON x402
  1. El cliente pide el recurso
  2. Recibe un 402 con el precio
  3. Paga con stablecoins (USDC)
  4. Accede. Sin cuenta ni API key
Agentes de IA → registrarse, cargar una tarjeta y pegar API keys son flujos de UI pensados para humanos. Un agente no puede hacerlo solo.
Y cobrar centavos por request no encaja en suscripciones mensuales ni en checkouts con tarjeta.
02 · El protocolo

¿Qué es x402?

Un protocolo abierto de pagos sobre HTTP que revive el código 402 Payment Required, “reservado para uso futuro” durante décadas.

CREADO POR COINBASE

Lo lanzó Coinbase Developer Platform el 6 de mayo de 2025. Su creador es Erik Reppel.

ESTÁNDAR ABIERTO

Licencia Apache-2.0. Hoy lo impulsa la x402 Foundation, bajo la Linux Foundation.

AGNÓSTICO

Pensado para cualquier red y token. Hoy: Solana, Base y otras EVM, Stellar, Aptos, Sui…

Meta: 1 línea en el server, 1 función en el cliente · 0 fees de protocolo
Foundation (jul 2026): 40 miembros, entre ellos Cloudflare, Google, Visa, Mastercard, Stripe, AWS y Solana Foundation.

El spec se arma en 3 capas
TYPESLos objetos: PaymentRequired, PaymentPayload, SettlementResponse
LOGICScheme + network: cómo se forma y verifica el pago
TRANSPORTPor dónde viaja: HTTP, MCP o A2A
Trust-minimizing: ni el facilitator ni el server pueden mover fondos fuera de lo que firmó el cliente.

05 · En el cable

3 headers HTTP

PAYMENT-REQUIRED
402 · server → cliente
lleva un PaymentRequired
PAYMENT-SIGNATURE
reintento · cliente → server
lleva un PaymentPayload
PAYMENT-RESPONSE
200 · server → cliente
lleva un SettlementResponse

Los tres viajan como JSON en base64.

// PAYMENT-REQUIRED decodificado (ejemplo)
{
  "x402Version": 2,
  "error": "PAYMENT-SIGNATURE header is required",
  "resource": { "url": "https://api.ejemplo.com/weather",
                "mimeType": "application/json" },
  "accepts": [{
    "scheme": "exact",
    "network": "solana:EtWTRABZaYq6iMfeYKouRu166VU2xqa1",
    "amount": "1000",            // 0,001 USDC (6 decimales)
    "asset": "4zMMC9srt5Ri…DncDU",  // mint de USDC
    "payTo": "<wallet del seller>",
    "maxTimeoutSeconds": 60,
    "extra": { "feePayer": "<pubkey del facilitator>" }
  }]
}
Spec v2 (actual). En v1 eran X-PAYMENT y X-PAYMENT-RESPONSE, y los requisitos iban en el body del 402.

El pago y el recibo

// PAYMENT-SIGNATURE → PaymentPayload
{
  "x402Version": 2,
  "accepted": {                // la opción elegida
    "scheme": "exact",
    "network": "solana:5eykt4Us…KZKvdp",
    "amount": "1000",
    "asset": "EPjFWdd5…wyTDt1v",
    "payTo": "2wKupLR9…JKkQfoxHDBg4",
    // … maxTimeoutSeconds, extra
  },
  "payload": {
    "transaction": "AAAA…="  // tx firmada
  }                              // por el cliente
}
// PAYMENT-RESPONSE → SettlementResponse
{
  "success": true,
  "transaction": "<firma de la tx>",
  "network": "solana:5eykt4Us…",
  "payer": "<pubkey>"
}

¿Y EN EVM?

El payload es signature (EIP-712) + authorization (EIP-3009): from, to, value, validAfter, validBefore, nonce.

STATUS CODES

402 sin pago o falló · 400 inválido
500 error · 200 pagado

Solana: el cliente firma un TransferChecked + Memo; la firma de fee payer la agrega el facilitator.
07 · Logic layer

Schemes y redes

exact

Monto fijo. Pagar un artículo, comprar créditos, un agente que paga una tool.

upto

Por uso: el cliente autoriza un máximo y se cobra lo consumido.

batch-settlement

Escrow + vouchers offchain que se liquidan juntos. EVM y Solana.

auth-capture

Autorizar ahora, capturar después. EVM.

08 · El rol clave

El facilitator

POST /verify

Valida firma, monto, red y destino. Solo lectura.

POST /settle

Envía la tx a la red y espera la confirmación.

GET /supported

Qué schemes, redes y signers soporta.

NO CUSTODIA

Nunca tiene tus fondos. Y es opcional: el server puede verificar y liquidar solo.

GASLESS PARA EL CLIENTE

En Solana, el server indica extra.feePayer: el facilitator agrega su firma como fee payer y paga la fee de red. El cliente solo firma la transferencia.

11 · Manos a la obra

Cómo empezar

SELLER $ npm i @x402/express @x402/core @x402/svm
BUYER $ npm i @x402/fetch @x402/core @x402/svm
// server.ts · Express + Solana devnet
import { paymentMiddleware, x402ResourceServer } from "@x402/express";
import { ExactSvmScheme } from "@x402/svm/exact/server";
import { HTTPFacilitatorClient } from "@x402/core/server";

const DEVNET = "solana:EtWTRABZaYq6iMfeYKouRu166VU2xqa1";
const facilitator = new HTTPFacilitatorClient({
  url: "https://x402.org/facilitator" });

app.use(paymentMiddleware({
  "GET /weather": {
    accepts: [{ scheme: "exact", price: "$0.001",
                network: DEVNET, payTo: svmAddress }],
    description: "Weather data" } },
  new x402ResourceServer(facilitator)
    .register(DEVNET, new ExactSvmScheme())));
// client.ts · fetch que paga solo
import { x402Client, wrapFetchWithPayment } from "@x402/fetch";
import { ExactSvmScheme } from "@x402/svm/exact/client";
import { createKeyPairSignerFromBytes } from "@solana/kit";

const signer = await createKeyPairSignerFromBytes(key);
const client = new x402Client();
client.register("solana:*", new ExactSvmScheme(signer));
client.setSpendControls({ maxAmountPerPayment: "$1" });

const fetchPaid = wrapFetchWithPayment(fetch, client);
const res = await fetchPaid("http://localhost:4021/weather");
// 402 → firma → reintento → 200, automático
